# `modules/s3Site`

Public S3 bucket serving the exported Next.js frontend over **S3 static website hosting**.

This is the interim hosting step. It exists so the app can be proven on a real URL before CloudFront is built; see `frontend_tutorial.md` §2.4.1 for the full deploy walkthrough and §2.5 for what changes when the CDN lands.

## Resources

| Resource | Purpose |
|---|---|
| `aws_s3_bucket.site` | The bucket. `force_destroy = true` — every object is regenerated by `bun run build`, so there is nothing here worth protecting from a `terraform destroy`. |
| `aws_s3_bucket_website_configuration.site` | Serves `index.html` for a directory, `404.html` for a miss. This is what makes `/login/` resolve at all. |
| `aws_s3_bucket_public_access_block.site_public_access` | All four flags **false**. This bucket is public by design. |
| `data.aws_iam_policy_document.site_public_read` | `s3:GetObject` for principal `*`. |
| `aws_s3_bucket_policy.site_public_read` | Attaches the above. |

## Inputs

| Name | Type | Description |
|---|---|---|
| `site_bucket_name` | `string` | Globally-unique bucket name, env suffix already applied by the caller (`local.site_bucket_name` in `envs/dev/main.tf`). |

## Outputs

| Name | Description |
|---|---|
| `site_bucket_name` | Bucket name/ID — the `aws s3 sync` target. |
| `site_website_endpoint` | Website endpoint host, no scheme. |
| `site_website_url` | Full `http://` URL of the site. |

## Footguns

**This is the only public bucket in the project.** The document bucket is locked down with a TLS-only policy and SSE-KMS; this one deliberately isn't either. It holds compiled HTML/JS only — no secrets. The Cognito pool ID and client ID baked into the bundle are identifiers, not credentials, and the API is guarded by its JWT authorizer regardless of who reads them.

**The bucket policy needs `depends_on` the public access block.** `PutBucketPolicy` is rejected with `AccessDenied` while `block_public_policy` is still on. Terraform can't infer the ordering — both resources only reference the bucket — so without the explicit `depends_on` the first apply fails and a second one succeeds. If you ever see a policy failing on a fresh apply and passing on retry, this is why.

**No `aws:SecureTransport` deny, unlike `modules/s3`.** S3 website endpoints are HTTP-only, so a TLS-only condition here would deny every request to the site. Add it back once CloudFront fronts the bucket.

**The website endpoint is HTTP, and that reaches into the frontend.** Two consequences the app has to carry until §2.5: `navigator.clipboard` is `undefined` outside a secure context (the demo-data copy rows need a fallback), and `next.config.ts` needs `trailingSlash: true` so the export writes `login/index.html` rather than `login.html` — S3 will not guess the `.html` for you, so a refresh on `/login` 404s without it.

**The site origin is built from the bucket name, not from this module's output.** `envs/dev/main.tf` composes `local.site_origin` as `http://<name>.s3-website-<region>.amazonaws.com` so it is known at plan time. Using `site_website_endpoint` there instead would make both CORS configurations show as "known after apply" on every plan.

## Cross-module dependencies

Nothing feeds into this module but its bucket name. It feeds **outward** into two CORS allow-lists in `envs/dev/main.tf` — the document bucket's (`document_bucket_cors_allow_origins`) and the API's (`api_cors_allow_origins`) — both via `local.site_origin`. Miss either one and the deployed site loads but every API call and the upload PUT fail preflight.
