# `modules/s3Site`

Private S3 bucket holding the exported Next.js frontend. It is the **origin** for the CloudFront distribution in `modules/cloudfront` — nothing reads it directly.

This module owns the bucket and its access settings only. The bucket **policy** lives in `modules/cloudfront`, because it needs the distribution ARN. See `frontend_tutorial.md` §2.5.

## Resources

| Resource | Purpose |
|---|---|
| `aws_s3_bucket.site` | The bucket. `force_destroy = true` — every object is regenerated by `bun run build`, so there is nothing here worth protecting from a `terraform destroy`. |
| `aws_s3_bucket_public_access_block.site_public_access` | All four flags **true**. The bucket is private; CloudFront reaches it with a signed request, not an anonymous one. |

Commented out in `s3.tf`, kept for history: `aws_s3_bucket_website_configuration.site` and the `site_public_read` policy pair. Both belonged to the interim S3-website-hosting setup and are incompatible with OAC — see Footguns.

## Inputs

| Name | Type | Description |
|---|---|---|
| `site_bucket_name` | `string` | Globally-unique bucket name, env suffix already applied by the caller (`local.site_bucket_name` in `envs/dev/main.tf`). |

## Outputs

| Name | Description |
|---|---|
| `site_bucket_name` | Bucket name/ID — the `aws s3 sync` target, and the bucket id `modules/cloudfront` attaches its policy to. |
| `site_bucket_arn` | For the OAC bucket policy's `Resource`. |
| `site_bucket_regional_domain_name` | REST endpoint host — the CloudFront origin. |

## Footguns

**Never re-enable the website configuration.** OAC cannot sign to an S3 website endpoint — AWS: it "doesn't apply to Amazon S3 origins that you configured as a website endpoint." Website endpoints are anonymous-only and cannot verify a signature, so turning it back on doesn't add a fallback, it just reopens a door the OAC design exists to close.

**Never add a second `aws_s3_bucket_policy` here.** A bucket holds exactly one policy, and `modules/cloudfront` already owns it. Two resources at different addresses have no dependency edge between them, so Terraform may apply them in either order and the plan shows nothing wrong — you'd get either a public bucket or no policy at all, at random. This is why the old `site_public_read` pair is commented out rather than kept "just in case".

**The four `block_public_*` flags being `true` does not block CloudFront.** They block *anonymous* access. OAC arrives as an authenticated AWS principal with a `SourceArn` condition, which is a different thing entirely. They also don't block `aws s3 sync`, which uses your IAM credentials.

**This bucket no longer has its own URL.** `local.site_origin` in `envs/dev/main.tf` is `module.cloudfront_origin.cloudfront_url`, and it feeds both CORS allow-lists. That value is unknown until the distribution is created, so both CORS configurations now show "known after apply" on a fresh plan — expected, not drift.

## Cross-module dependencies

**In:** nothing but the bucket name.

**Out:** all three outputs feed `modules/cloudfront` — the name (OAC name, function name prefix, policy target), the ARN (policy `Resource`), and the regional domain name (the origin). `site_bucket_name` also targets the `aws s3 sync` in `terraform_data.site_deploy`.
